# Fault injection: первые ручные эксперименты

Цель: научиться управляемо вносить сбои в стенд и посмотреть, какие из уже
имеющихся сигналов (логи, метрики RED) их показывают, а какие нет.

## Условия

- Стенд: gateway → users (через toxiproxy), gateway → orders (напрямую).
- Таймаут HTTP-клиента gateway: 3 с. Вызовы последовательные: сначала users, потом orders.
- Нагрузка: один запрос `GET /api/users/42` каждые 0.5 с (цикл curl).
- Наблюдение: код и время ответа (curl), JSON-логи gateway, метрики `/metrics` gateway.
- Ветка: `fault-injection`.

## Инструменты

- **toxiproxy** (TCP-прокси на канале gateway → users) — сбои канала.
- **docker compose pause / kill** — сбои контейнера (без Pumba, на первом этапе).

## Результаты

| # | Сбой | Команда | Ожидание | Факт | 
|---|------|---------|----------|------|
| 0 | Нет (baseline) | — | 200, единицы мс | 200, 0.003–0.019 с |
| 1 | Задержка 500 мс на канале users | toxiproxy `latency 500` | 200, ~0.5 с | 200, 0.506–0.520 с |
| 2 | Канал молчит | toxiproxy `timeout 0` | 502, ~3 с | 502, ~3 с, `status=error` у users |
| 3 | Канал разорван | toxiproxy `enabled=false` | 502, ~0 с | 502, единицы мс, `status=error` у users |
| 4 | Контейнер users заморожен | `docker compose pause users` | 502, ~3 с | 502, ~3 с, `status=error` у users |
| 5 | Контейнер orders убит | `docker compose kill orders` | 502, ~0 с, connection refused | 502, 8 мс, ошибка **no such host** |

Пример лога из эксперимента 5:

```
"msg":"http_client_request","target":"orders","status":"error","duration_ms":7
"msg":"orders call failed","err":"... dial tcp: lookup orders on 127.0.0.11:53: no such host"
"msg":"http_request","route":"/api/users/{id}","status":502,"duration_ms":8
```

Итоговые метрики gateway после всех экспериментов:

```
http_client_requests_total{status="200",   target="users"}  7548
http_client_requests_total{status="error", target="users"}  37
http_client_requests_total{status="200",   target="orders"} 7526
http_client_requests_total{status="error", target="orders"} 22
http_requests_total{path="/api/users/{id}", status="200"}   7526
http_requests_total{path="/api/users/{id}", status="502"}   59
```

## Наблюдения

1. **Все сбои управляемы и повторяемы.** Каждый включается и выключается одной
   командой, после выключения система возвращается к baseline без перезапуска.

2. **Метрики согласованы между собой.** 502 на входе (59) = ошибки users (37) +
   ошибки orders (22). Вызовов orders всего 7526 + 22 = 7548 — ровно столько,
   сколько было успешных вызовов users. Это подтверждает по метрикам, что при
   отказе users gateway до orders не доходит (последовательная схема).

3. **Задержка складывается с обычным временем запроса**, а не заменяет его
   (500 мс + ~10 мс). Коды ответа при этом не меняются — такой сбой виден
   только по длительности.

4. **Разные отказы сливаются в один счётчик.** Эксперименты 2–5 дают одинаковый
   внешний результат (502) и одинаковую метку `status="error"`. Различаются они
   только длительностью (~3 с при зависании, единицы мс при разрыве) и текстом
   ошибки в логе.

5. **Зависание процесса неотличимо от молчащего канала.** Со стороны gateway
   эксперименты 2 (toxiproxy) и 4 (pause) выглядят одинаково: ответа нет до
   таймаута клиента.

6. **Убитый контейнер в Docker — это не «отказ соединения», а исчезновение имени.**
   Docker удаляет остановленный контейнер из своего DNS (127.0.0.11), поэтому
   ошибка — `no such host`, а не `connection refused`. В реальной сети с живым
   хостом картина была бы другой; это особенность среды, которую нужно учитывать
   при переносе выводов.

## Выводы для наблюдаемости

- Одной метрики ошибок недостаточно: без гистограммы длительности разрыв и
  зависание неразличимы.
- Метку `status="error"` стоит разбить по причине (таймаут / отказ соединения /
  DNS), чтобы класс отказа был виден прямо в счётчике, а не только в логах.
- Чтобы отличить «процесс завис» от «молчит сеть», нужен сигнал от самой
  зависимости (например, её собственные метрики или health-check), а не только
  взгляд со стороны вызывающего сервиса.

## Ограничения

- Ручной запуск, одна нагрузка, под прокси только канал users.
- Потери пакетов на уровне L3 (netem/Pumba) не проверялись.
- Нет централизованного сбора метрик: значения сняты вручную с `/metrics`.

## Следующие шаги

1. Потери пакетов и jitter через Pumba netem, сравнение с задержкой toxiproxy.
2. Частичная деградация (toxicity 0.3) — бимодальное распределение латентности.
3. Добавить в метрики клиента причину ошибки и повторить эксперименты 2–5.
